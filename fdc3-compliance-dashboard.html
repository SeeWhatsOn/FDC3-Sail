Executive View

Working

The core package has the right composable shape: transport abstraction, browser WCP split, injected app launcher, app directory, validator, logger, user channels, implementation metadata, and intent resolver callback.

Not Yet Compliant

It should not claim full FDC3 2.2 compliance until remaining production-readiness items (for example logging hygiene and docs alignment) are addressed.

Production Risk

DACP/WCP payload logging can expose sensitive context data. Documentation also contains package-name drift and overstates built-in validation.

Dependency Order

  1. Channel state model first, because it affects user and app channel routing.
  2. PrivateChannel catch-all listeners can run independently.
  3. Heartbeat cleanup should coordinate with circular-import cleanup. — done: timeout uses shared cleanupDACPHandlers; timers live in heartbeat-runtime.ts.
  4. Logging and docs can be done after behavior blockers.
  5. Platform contract tests come after the core contract stabilizes.

Blockers And Drill-Down

User and app channel state are conflated

Blocker

AppInstance.currentChannel currently represents both current user channel and app-channel listener participation. FDC3 treats getCurrentChannel() and leaveCurrentChannel() as user-channel APIs.

Where to change and why

Files likely touched

Specific changes

  • Add a separate app-channel participation/listener routing structure.
  • Keep current user channel membership distinct from app-channel listeners.
  • Update selectors so app-channel broadcast fan-out does not rely on user-channel state.
  • Update default broadcast to use the current user channel only.

Acceptance criteria

  • getCurrentChannel() reports only the current user channel.
  • Adding an app-channel listener does not replace the current user channel.
  • Default broadcast() still targets the joined user channel after app-channel listener registration.

Future API: app-channel clear context

Not FDC3 2.2

Exact FDC3 v2.2 docs do not include Channel.clearContext() or app-channel contextCleared conformance tests. These appear in newer/next docs, so they should be treated as future-version or Sail extension work, not a 2.2 blocker.

Logging is not safely configurable or OTEL-ready

Required

DACP/WCP messages are app-originating input and may contain client, trade, portfolio, or other sensitive data. Logging must be configurable for off, production, development, and explicit debug modes, while OpenTelemetry support should emit safe structured logs/spans without coupling the pure core to a concrete exporter.

Where to change and why

OpenTelemetry design target

  • Keep @finos/sail-desktop-agent core vendor-neutral: define a small observability interface and safe metadata model in core; adapt it to OTEL in sail-platform-api or a dedicated adapter.
  • Follow the OTEL Logs Data Model fields: timestamp, severity text/number, body, attributes, event name, and optional trace/span context.
  • Follow OTEL messaging semantic conventions where applicable: messaging.system, messaging.operation.name, messaging.operation.type, messaging.message.id, and messaging.message.conversation_id.
  • Use Sail/FDC3-specific low-cardinality attributes such as fdc3.message.type, fdc3.context.type, fdc3.intent.name, fdc3.channel.id, fdc3.source.instance_id, and fdc3.destination.instance_id.

Logs and telemetry to add

Task 4 Add safe configurable logging and OTEL observability

Replace ad hoc logging with a configurable observability layer. Production defaults must emit safe metadata only; development and debug diagnostics must be explicit; OTEL support should be adapter-based so core remains vendor-neutral.

Dependencies
None
Estimated scope
Medium
Verification
Add logger/telemetry tests with sensitive context payloads; run package tests.

Files likely touched

packages/sail-desktop-agent/src/core/interfaces/logger.ts packages/sail-desktop-agent/src/core/desktop-agent.ts packages/sail-desktop-agent/src/core/handlers/types.ts packages/sail-desktop-agent/src/core/dacp-protocol/dacp-utils.ts packages/sail-desktop-agent/src/core/handlers/dacp/context-handlers.ts packages/sail-desktop-agent/src/core/handlers/dacp/intent-handlers/intent-raise-intent.ts packages/sail-desktop-agent/src/core/handlers/dacp/wcp-handlers.ts packages/sail-desktop-agent/src/browser/wcp/wcp-message-routing.ts packages/sail-desktop-agent/src/browser/wcp/message-port-transport.ts packages/sail-desktop-agent/src/browser/wcp/wcp-intent-resolver.ts packages/sail-desktop-agent/src/core/app-directory/app-directory-manager.ts packages/sail-platform-api/**/otel*

Recommended architecture

  • Keep OpenTelemetry SDK dependencies out of the pure desktop-agent core. Core should expose a small Observability or TelemetrySink interface with safe structured events and optional span lifecycle hooks.
  • Implement OTEL wiring in sail-platform-api or a dedicated adapter that maps Sail events to OTEL logs, spans, metrics, resources, and exporters.
  • Add config such as observability.mode with off, production, development, and explicit debug. Do not enable payload logging by default in any mode.
  • Map logger levels to OTEL severity ranges: debug to 5-8, info to 9-12, warn to 13-16, and error to 17-20.
  • Use OTEL messaging conventions for message-oriented spans: messaging.system, messaging.operation.name, messaging.operation.type, messaging.message.id, and messaging.message.conversation_id.

Concrete implementation contract

  • The core package must not import @opentelemetry/*. If OTEL packages are added, they belong in sail-platform-api or a dedicated adapter.
  • Add a core config shape equivalent to: observability?: { mode?: "off" | "production" | "development" | "debug"; logger?: Logger; telemetry?: TelemetrySink }.
  • Add TelemetrySink in core with a minimal API: emit(event: ObservabilityEvent): void and optional startSpan(name, attributes) returning a small span-like object with end(), recordException(error), and setAttribute(key, value).
  • Add ObservabilityEvent with eventName, severity, message, attributes, optional errorType, and optional timestamp. Attribute values must be primitives or arrays of primitives.
  • Default mode is production. In production, emit warn/error/info metadata only and suppress debug. In off, emit nothing. In development and debug, emit extra lifecycle metadata but still do not serialize full context or raw messages.

Safe versus forbidden attributes

  • Allowed by default: message type, request UUID, response UUID, event UUID, source instance ID, destination instance ID, app ID, context type, intent name, channel ID, booleans such as hasPayload/hasContext, counts, duration, and low-cardinality error type.
  • Forbidden by default: payload.context, full payload, raw message objects, raw MessageEvent, serialized JSON payloads, account IDs, client names, trade IDs, portfolio IDs, positions, orders, tokens, credentials, cookies, and arbitrary context properties beyond type.
  • Do not add an unsafe payload logging option in this task. If needed later, it must be a separate explicitly named feature with production safeguards.

Mode behavior matrix

off
No logger output, no telemetry events, no spans.
production
Default. Info/warn/error metadata only, no debug, no payload serialization.
development
Adds lifecycle/routing details and debug-level metadata, still no raw payloads or context serialization.
debug
Most verbose safe mode. Includes additional validation/routing state but still uses the same redaction rules as production.

Test-first checklist

  • Add src/core/__tests__/observability-redaction.test.ts first. It should fail before implementation by proving sensitive values reach the current logger.
  • Add tests for off, production, development, and debug mode behavior.
  • Add tests for DACP broadcast, raise intent, WCP4 validation, invalid app message routing, and MessagePort broadcast receipt with accountNumber: "SECRET-123" and clientName: "SECRET-CLIENT".
  • Add an adapter-facing unit test with a fake TelemetrySink and assert OTEL-style attributes contain safe keys only.
  • Add a static consistency test that fails if @opentelemetry/ imports appear under packages/sail-desktop-agent/src.

No-ambiguity implementation notes

  • Create summarizeDACPMessage(message) / summarizeWCPMessage(message) helpers returning only safe fields: message type, request/response/event IDs, source/destination instance IDs, context type, intent name, channel ID, and high-level booleans such as hasPayload and hasContext.
  • Introduce a structured event shape with fields for eventName, severity, message, and safe attributes.
  • Replace full-message logging in router, WCP bridge, DACP utilities, broadcast, and intent handlers with the summary helpers.
  • Do not log raw invalid messages. Log typeof message, detected type if present, validation phase, and rejection reason.
  • Remove fullMessage: JSON.stringify(...), broadcastEventPayload: JSON.stringify(...), contextPayload: JSON.stringify(...), and validatedContext: JSON.stringify(...) from default logs.
  • Pass injected logger/observability into browser transports and app-directory paths that currently use global consoleLogger.
  • Add telemetry around DACP request handling, WCP identity validation, app-to-agent routing, agent-to-app routing, broadcast fan-out, intent resolution, malformed message rejection, and cleanup.
  • Add tests with fake sensitive fields such as accountNumber: "SECRET-123" and clientName: "SECRET-CLIENT"; assert neither logger calls nor telemetry attributes contain those values by default.

Logs and spans to add

  • DACP request processing: one span/event per request type with fdc3.message.type, request ID, source instance ID, and result.
  • WCP identity validation: span for WCP4/WCP5 with app ID, origin match result, reconnect flag, and low-cardinality error type.
  • Routing: app-to-agent and agent-to-app route events with source, destination, message type, and transport state.
  • Broadcast fan-out: event with channel ID, context type, target count, success count, and failure count.
  • Intent resolution: span covering handler lookup, resolver callback, launch path, delivery scheduling, and failure classification.
  • Cleanup: event for WCP6 goodbye, disconnect, and heartbeat timeout with counts for listeners, private channels, pending intents, and heartbeat state removed where available.

Acceptance criteria

  • Logging can be disabled completely.
  • Production mode emits safe metadata only and never serializes full context.
  • Development/debug logging is explicit and still redacts sensitive context by default.
  • OTEL adapter can emit logs/spans/events with OTEL-compatible severity, event names, messaging attributes, and optional trace/span correlation.
  • Full payload.context, raw invalid messages, and browser MessageEvent objects are not stringified by default.
  • Tests prove sensitive values do not reach logger arguments or telemetry attributes.
  • Comments and README/API docs accurately describe logging modes, OTEL adapter expectations, and the no-payload default.
